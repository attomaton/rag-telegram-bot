# Mini-RAG: каталог товаров → эмбеддинги → Chroma / pgvector → Telegram-бот

Учебный, но рабочий RAG: бот-консультант отвечает на вопросы покупателей **только** по товарам из каталога.

```
                 ИНДЕКСАЦИЯ (ingest.py, один раз / при обновлении каталога)
catalog.csv ──► Product.to_document() ──► Embedder("passage: …") ──► VectorStore.upsert
                                                                     (Chroma | pgvector)

                 ЗАПРОС (bot.py / ask.py)
вопрос ──► extract_filters()  ── «до 10 тысяч», «в наличии» ──┐
      └──► Embedder("query: …") ──► VectorStore.search(20 кандидатов, filters)
                                                   ▼
                              Reranker (cross-encoder): оценка каждой пары (вопрос, товар)
                                                   ▼
                                  top-5, порог по оценке реранкера
                                                   │ ниже порога → «не нашёл»
                                                   ▼
                                  Claude: system-промпт + <catalog>найденные товары</catalog> + вопрос
                                                                            ▼
                                                                     ответ в Telegram
```

## Быстрый старт (Windows / PowerShell)

```bash
python -m venv .venv
```
```bash
.venv\Scripts\pip install -r requirements.txt
```
```bash
copy .env.example .env
```

Заполните в `.env`: `TELEGRAM_BOT_TOKEN` (от [@BotFather](https://t.me/BotFather)) и `ANTHROPIC_API_KEY`.

```bash
.venv\Scripts\python ingest.py --reset
```
```bash
.venv\Scripts\python ask.py "наушники для бега до 10 тысяч"
```
```bash
.venv\Scripts\python bot.py
```

`ask.py --no-llm "…"` — только поиск, без Claude: удобно настраивать ретрив; `--no-rerank` — без реранкера, для сравнения.
В боте команда `/debug` показывает найденные товары с оценками: `rr` — реранкер, `vec` — косинусная близость.

При первом запуске скачиваются модели: эмбеддинги (~470 МБ) и реранкер (~2,2 ГБ). Кеш — в `./.hf_cache` (переопределяется `HF_HOME`).

### pgvector вместо Chroma

```bash
docker compose up -d
```
В `.env`: `VECTOR_STORE=pgvector`, затем снова `python ingest.py --reset`. Код бота не меняется — оба хранилища реализуют один интерфейс (`minirag/stores/base.py`).

## Что этот проект показывает (шпаргалка к вопросам про RAG и векторные БД)

**Зачем RAG.** LLM не знает ваш каталог, цены и остатки, а дообучать её под каждое изменение дорого. RAG на каждый вопрос находит релевантные документы и кладёт их в промпт — модель отвечает по свежим данным, а ответ можно проверить по источникам. Обновить знания = переиндексировать CSV.

**Эмбеддинг** — вектор, в котором близкие по смыслу тексты оказываются рядом. Поэтому запрос «чем убирать шерсть кота» находит робот-пылесос и вертикальный пылесос с турбощёткой, хотя слова «кот» в описаниях нет. Важные детали:
- запрос и документы кодируются **одной и той же** моделью; смена модели = полная переиндексация (размерность и пространство другие);
- у E5 есть префиксы `query:` / `passage:` — без них качество падает;
- векторы нормализованы → косинусная близость = скалярное произведение.

**Чанкинг.** Здесь один товар = один чанк: описания короткие. Для длинных документов (инструкции, отзывы) режут на куски по ~300–500 токенов с перекрытием и хранят ссылку на исходный товар.

**Векторная БД** хранит векторы и умеет быстро искать k ближайших. Точный перебор — O(N); на миллионах записей используют приближённые индексы (ANN): **HNSW** (граф, быстрый и точный, много памяти) или **IVFFlat** (кластеры, дешевле, нужно обучение на данных). Оба хранилища здесь используют HNSW с косинусной метрикой.

**Chroma vs pgvector:**

| | Chroma | pgvector |
|---|---|---|
| Запуск | `pip install`, файл на диске | Postgres + расширение |
| Фильтры | `where` по метаданным | полноценный SQL, джойны с заказами/остатками |
| Транзакции, бэкапы, права | минимально | всё, что умеет Postgres |
| Когда брать | прототип, локальные эксперименты | уже есть Postgres, нужны консистентность и SQL |

Ещё варианты: Qdrant, Weaviate, Milvus (выделенные векторные БД с шардированием), FAISS (библиотека, не БД).

**Гибридный поиск: вектор + фильтры.** Эмбеддинги плохо понимают числа: «до 10 тысяч» и «до 100 тысяч» для них почти одинаковы. Поэтому цена и наличие извлекаются правилами (`extract_filters`) и применяются **внутри БД вместе с векторным поиском** (pre-filtering). Если фильтровать после top-k (post-filtering), подходящие товары могут не попасть в выдачу. Следующий шаг — смешивать векторный поиск с полнотекстовым BM25 (точные артикулы, бренды) через Reciprocal Rank Fusion.

**Реранкер (двухэтапный поиск).** Эмбеддинг-модель — *bi-encoder*: запрос и товар кодируются по отдельности, векторы товаров посчитаны заранее, поэтому поиск по индексу мгновенный, но сравнивается лишь «общий смысл». *Cross-encoder* читает пару «вопрос + товар» целиком и видит, как они соотносятся, — это намного точнее, но требует прогона модели на каждую пару. Поэтому этапы комбинируют: вектор быстро отбирает 20 кандидатов (recall), реранкер сортирует их и отсекает лишнее (precision).

Замеры на этом каталоге (`ask.py --no-llm` / `--no-rerank`):

| Запрос | Только вектор (cosine) | После реранкера |
|---|---|---|
| посоветуй стиральную машину | пылесос 0.85 — выше порога, ложное совпадение | 0.001 → «не нашёл» ✅ |
| привет | 0.78 | 0.006 → «не нашёл» ✅ |
| ноутбук для монтажа видео | Lumen Pro 0.88, Basic 15 0.85, монитор 0.84 — почти равны | Lumen Pro **0.975**, Basic 15 0.02 ✅ |
| монитор для работы с фото | View 27 4K 0.87, View 24 Office 0.87 | 4K **0.97**, Office 0.06 ✅ |
| телефон, который долго держит заряд | Rugged R2 0.858 = Nova Lite 0.858, Pocket Mini 0.855 | Nova Lite («держит два дня») **0.41**, остальные ≤ 0.08 ✅ |

**Пороги.** Векторный поиск всегда что-то вернёт, даже на «какая погода в Москве», и косинусная близость плохо разделяет «по теме / не по теме»: у E5 все оценки сжаты в 0.75–0.90, а «стиральная машина» (0.85) обходит часть настоящих запросов. Оценка реранкера (0..1) разделяет лучше, но её масштаб сильно зависит от запроса: «монитор для фото» → 0.97, «подарок любителю кофе» → 0.012. Поэтому порог из двух частей:
- `RERANK_MIN_SCORE=0.01` — если даже лучший кандидат ниже, бот отвечает «не нашёл» и **не вызывает LLM** (оффтоп на этом каталоге даёт ≤ 0.006);
- остальные товары остаются, если прошли тот же абсолютный порог **или** набрали ≥ `RERANK_RELATIVE=0.1` от лучшего.

Пороги подобраны на десятке запросов — на реальном трафике их калибруют по размеченной выборке. Без реранкера (`RERANKER_MODEL=` пусто) работает старый порог `MIN_SCORE` по косинусу.

**Цена реранкера — задержка.** `bge-reranker-v2-m3` (568M параметров) на CPU этого ноутбука обрабатывает 20 пар за **~8 с**; на GPU — доли секунды. Как ускорить: меньше кандидатов (`RERANK_CANDIDATES=10` — вдвое быстрее), ONNX + int8-квантизация (обычно в 2–4 раза на CPU), GPU или облачный rerank-API. Лёгкая альтернатива `DiTy/cross-encoder-russian-msmarco` работает за ~1,5 с, но на этом каталоге хуже: «привет» получает 0.55, а «чем убирать шерсть кота» — 0.001, так что отсекать по ней оффтоп нельзя.

**Борьба с галлюцинациями.** Системный промпт требует отвечать только по `<catalog>`, контекст передаётся структурно (id, цена, наличие в атрибутах), а без найденных товаров LLM не вызывается вообще.

**Как оценивать качество.** Отдельно ретрив и генерацию: для ретрива — набор «вопрос → ожидаемые id товаров» и метрики recall@k / MRR; для генерации — проверка, что ответ опирается на контекст (faithfulness) и отвечает на вопрос.

**Что улучшить дальше:** ускорение реранкера (ONNX/int8); переписывание уточняющих вопросов («а подешевле?») в самостоятельный запрос с учётом истории диалога; инкрементальная переиндексация по хешу описания; LLM-извлечение фильтров вместо регулярок.
